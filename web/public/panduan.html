Why can an account be suspended?

The GitHub Actions terms effective 27 August 2026 restrict GitHub-hosted runners from developing, testing, deploying, or distributing software related to repos. The terms also warn that use outside those bounds can result in jobs being terminated, Actions being limited, repos disabled, or accounts suspended.

Seiji-PC holds Windows runners up to six hours and provides an RDP desktop for general use. This pattern risks being classified as using Actions as a remote desktop service rather than CI/test for projects. Repo ownership checks, private repos, Tailscale, or valid secrets do not change that intended use.

GitHub notifications are the authoritative source for the specific reason for each account. If a suspension occurred for another reason, only the account owner and GitHub Support can confirm.

Safe steps to take now

  1. Do not press start or dispatch workflows. The dashboard/API buttons are blocked. New jobs from the main workflow are skipped before runner creation.
  2. Do not create other accounts/repos to avoid suspension. That can worsen the review.

Login on every refresh & why the dashboard can cause suspension (vs safe manual fork)

Login on every refresh (fixed): the dashboard session is stored in cookies ghs (GitHub) & sid (admin) encrypted with AES-256-GCM + SESSION_SECRET + Max-Age. Old bug: fetch without credentials:'include' caused cookies not to be sent → /api/auth/status returned without mode → frontend forced showLogin() on each reload. Fix now: fetch(...,{credentials:'include'}), SESSION_TTL_DAYS 7→30 days, ADMIN_TTL 12 hours→30 days, plus caching localStorage: xyrdp_me_cache so refresh enters the app first while background verification runs. Ensure SESSION_SECRET on Vercel is not rotated frequently (rotating invalidates all old cookies).

Why "Sign in with GitHub" via the dashboard is more likely to cause suspension than a manual fork?

  • Manual fork (click "Use this template" / Fork on github.com): native GitHub action, rate limited per your account, the forked repo becomes you/Seiji-PC and workflows run in your repo using your token. It does not go through the Vercel/dashboard IP. Safest option.
  • Dashboard "Sign in with GitHub" (OAuth App): after OAuth, the dashboard uses your token to POST /repos/{owner}/{repo}/generate (create repo from template), PUT /actions/secrets, and POST /actions/workflows/.../dispatches — all via API calls from Vercel's IP (xyrdp-dash.vercel.app). If many users click "Create Repo" + "Start" repeatedly within the same minutes, GitHub may detect this as abuse/automation spam (repo generate + workflow_dispatch spam from a single IP/OAuth app) → flagged → suspension.
The dashboard is now rate-limited: max 2× Start per 5 minutes per user/IP + block dispatch if there is a run queued/in_progress (must Stop first). This reduces GitHub spam detection.

Safe dashboard usage (to avoid suspension):

  1. Safest: manually fork first on github.com → open xykal/Seiji-PC → Use this template → Create a new repository (name it Seiji-PC) → then sign into the dashboard (it will automatically use your/Seiji-PC).
  2. Do not spam "Create Repo" or "Start" — wait for runs to finish. If you create a new repo, wait 1–2 minutes before starting.
  3. Set secrets RDP_PASSWORD & TAILSCALE_AUTH_KEY (do not share tskey-auth-... publicly). NGROK_AUTHTOKEN if you use ngrok.
  4. Do not use one account to create 5+ RDP repos within an hour — that pattern is most frequently flagged as spam.
  5. Dashboard login now persists for 30 days — no need to log in every refresh. If you're still prompted to log in: clear the ghs/sid cookies → log in again, or check Vercel's SESSION_SECRET (≥32 chars, avoid rotation). Logout → clear localStorage cache.

Note: GitHub policy of 27 Aug 2026 still applies — GitHub runners are not for public RDP use of 6 hours. This guide only reduces automation spam risk, it does not change the Terms.

Wallpaper technical status

We found that the old script assumed wallpaper succeeded without checking Windows function results and wrote settings to the runner/default profile, not always to the RDP session the user was viewing. Since new sessions are paused, wallpaper changes will not be applied or tested now. "Success" status in old logs does not prove the image displayed on the desktop. Fixes need to be tested on a desktop host that actually allows RDP access.
