Why can an account be suspended?

GitHub Actions terms effective August 27, 2026 restrict GitHub-hosted runners from developing, testing, deploying, or publishing software related to repositories in certain ways. The terms also warn that usage outside those bounds can result in jobs being stopped, Actions being restricted, repositories disabled, or accounts suspended.

Seiji-PC holds Windows runners up to six hours and provides an RDP desktop for general use. This pattern risks being treated as using Actions as a remote desktop service, not CI/test for a project. Repository owner checks, private repos, Tailscale, or valid secrets do not change that intended use.

GitHub notifications are the authoritative source for the specific reason for each account. If a suspension happened for another reason, only the account owner and GitHub Support can confirm.

Safe steps now

  1. Do not press start or dispatch workflows. Dashboard/API buttons are blocked. New jobs from the main workflow are skipped before runner creation.
  2. Do not create another account/repo to avoid suspension. That can worsen the review.
  3. For old template copies, open Actions, select the Seiji-PC workflow, open the … menu, then choose Disable workflow. Old template copies are not updated automatically.
  4. If you no longer use a session network, open Tailscale Admin → Settings → Keys and revoke the related auth key. If there are non-ephemeral nodes, remove unknown nodes under Machines.
  5. In old GitHub repos, open Settings → Secrets and variables → Actions. Remove secrets that are no longer used; GitHub does not reveal stored secret values.

Login on every refresh & why the dashboard can cause suspension (vs safe manual fork)

Login on every refresh (fixed): dashboard sessions are stored in cookies ghs (GitHub) & sid (admin) encrypted with AES-256-GCM + SESSION_SECRET + Max-Age. Old bug: fetch without credentials:'include' caused cookies not to be sent → /api/auth/status returned without mode → frontend forced showLogin() on every reload. Fix now: fetch(...,{credentials:'include'}), SESSION_TTL_DAYS 7→30 days, ADMIN_TTL 12 hours→30 days, plus a localStorage: xyrdp_me_cache cache so refresh enters the app while background verification runs. Ensure SESSION_SECRET on Vercel is not rotated frequently (if changed, all old cookies become invalid).

Why “Sign in with GitHub” via the dashboard is riskier for suspension than a manual fork?

  • Manual fork (click “Use this template” / Fork on github.com): native GitHub action, rate-limited per your account, resulting fork becomes you/Seiji-PC and workflow runs in your repo using your token. Does not go through Vercel/dashboard IP. Safest option.
  • Dashboard “Sign in with GitHub” (OAuth App): after OAuth, the dashboard uses your token to POST /repos/{owner}/{repo}/generate (create a repo from template), PUT /actions/secrets, and POST /actions/workflows/.../dispatches — all via the API from Vercel IP (xyrdp-dash.vercel.app). If many users click “Create Repo” + “Start” repeatedly in the same minutes, GitHub can detect this as abuse/automation spam (repo generate + workflow_dispatch spam from one IP/OAuth app) → flagged → suspension.
The dashboard is now rate-limited: max 2× Start per 5 minutes per user/IP + block dispatch if there is any run queued/in_progress (must Stop first). This is to avoid GitHub spam detection.

Safe ways to use the dashboard (to avoid suspension):

  1. Safest: manually fork first on github.com → open Seijii-Dev/XyRd → Use this template → Create a new repository (name it Seiji-PC) → then sign in to the dashboard (it will use you/Seiji-PC automatically).
  2. Do not spam “Create Repo” or “Start” — wait for the run to finish. If creating a new repo, wait 1–2 minutes before starting.
  3. Fill secrets RDP_PASSWORD & TAILSCALE_AUTH_KEY (do not share tskey-auth-... publicly). NGROK_AUTHTOKEN if using ngrok.
  4. Do not use one account to create 5+ RDP repos within an hour — that is the spam pattern most frequently flagged.
  5. Dashboard login now persists 30 days — you should not need to sign in on every refresh. If still asked to sign in: clear ghs/sid cookies → sign in again, or check Vercel SESSION_SECRET (≥32 chars, avoid rotating). Logout → clear localStorage cache.

Note: GitHub policy of Aug 27, 2026 still applies — GitHub runners are not for general 6-hour RDP use. This guidance only reduces automation spam risk, not change the Terms.

Wallpaper technical status

We found older scripts assumed wallpaper succeeded without checking the Windows function result and wrote settings to the runner/default profile, not always to the RDP session the user sees. Because new sessions are paused, wallpaper changes will not be applied or tested now. A “success” status in old logs does not prove the image appeared on the desktop. Fixes need testing on a desktop host that allows RDP access.

Need a remote desktop?

Use Windows/remote desktop services that explicitly allow interactive access per their plans and policies. Once a suitable host is chosen, guidance can be rebuilt from scratch — including Tailscale HP, Tailscale admin access, key management, GitHub secrets if still needed, and wallpaper diagnosis.

The dashboard is currently only for monitoring old repos/runs and managing secrets. Automatic set-secret features in the dashboard are intentionally disabled during the pause.
